# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`@tomcog/case-study`: one builder and one player for a project — a list of steps, each displaying a slide, a running app, a framed URL or an image — packaged as a React 18/19 component library. Peer deps: `@tomcoggia/ui` (0.86+), `react`, `react-dom`, `motion` (11+). The only runtime dependency is `lucide-react`. It also contains **ProjectBuilder** (`app/`), a standalone app for creating, managing and editing projects. README.md covers both.

## Commands

```bash
npm install
npm run dev       # ProjectBuilder on http://localhost:5187 (Vite, imports src/ directly, so no rebuild needed)
npm run build     # tsc -p tsconfig.json → dist/ (the package)
npm run watch     # tsc --watch → dist/
npm run check     # type-check the package and the app
npm run build:app # read-only ProjectBuilder site → app-dist/ (gitignored)
```

There are no tests and no linter. `npm run check` is the only check. To see a package change running, use `npm run dev`. To see it inside a host app, link the package from the app with `"@tomcog/case-study": "file:../ProjectBuilder"` and `resolve.dedupe: ["react", "react-dom", "motion"]` in its Vite config.

## dist/ is committed

Installs from GitHub use the committed `dist/`, because npm 11 doesn't run a git dependency's `prepare` script unless it's approved. After changing `src/`, run `npm run build` and commit `dist/` along with the source. Rebuild before tagging a release. Releases install from the tag's tarball (`.../archive/refs/tags/vX.Y.Z.tar.gz`).

## Architecture

- **Data model** (`src/core.tsx`, `src/walkthrough/types.ts`): a project is one JSON object — an ordered list of `steps` plus a `preview` card. There are no project kinds: a deck of slides is a project whose every step displays one. Each step says for itself which app it runs, what it displays and what it does. A slide is a `Screen`, with a `layout` (`cover`, `overview`, `basic1`, `basic2`, `quote`, `metrics`, `gallery`, `showcase`, `bento`, `video`) and one flat bag of optional fields, and which of them it uses depends on its layout. The package only renders and edits the object; the host app stores it.
- **Rendering** (`src/core.tsx`): `ScreenView` renders any screen onto a fixed 1280×720 canvas (`STAGE_W`/`STAGE_H`). `Stage` scales that canvas to fit its parent, and `bleedBg`/`backdropFor` fill the letterbox margins around it. All layout math is in stage pixels. The `B_*` constants hold the spacing for the Basic templates. Entrance animations use the motion variants in core (`screenVariants`, `buildContainer`/`buildItem`), and each has a reduced-motion version.
- **Player** (`src/walkthrough/WalkthroughPlayer.tsx`, exported as `ProjectPlayer`): a panel of copy beside the frame for most steps. A slide has no panel — it carries its own copy — so it covers the whole viewport, with click, ArrowRight and Esc as a deck has. It is drawn *over* the frame rather than instead of it, so the app underneath keeps running: a slide between two demo steps costs the reader nothing. Crossing between the two chromes is a crossfade.
- **Text markup** (`src/ui/renderStyledText.tsx`): screen text fields are plain strings with a small inline syntax: `{red}`, `**bold**`, `{**bold red**}`, `[label](url)` for a link, `[gray]` for muted text. Stored copy relies on it, so changing the syntax breaks existing projects. The other files in `src/ui/` are the shared presentational pieces (device frames, lightbox, preview card, image library modal).
- **Slides** (`src/slide.tsx`): the ten layouts and the fields each uses. `layoutPatch` seeds default list content (the `DEFAULT_*` constants in core) the first time a slide switches layout, so the canvas never shows an empty shell. `SlideFields` is the whole inspector body for a slide, used by the one builder — one set of controls, so they can't drift.
- **Walkthroughs** (`src/walkthrough/`): stepped copy in a side panel beside whatever the step is about. `WalkthroughPlayer.tsx` plays one, `WalkthroughBuilder.tsx` edits it, and `stage.tsx` holds the frame, scaling, measuring and overlays they share. There is no fixed canvas here — the frame gets a real viewport width and scales to fit it — so none of the `STAGE_*` math applies.
- **A step says three things for itself** (`src/walkthrough/types.ts`), and they are independent: `app` is the ingested app **running** (absent is "none", a choice rather than a fallback); `content` is what is **visible** (the app, an `embed` URL, or an `image` — the app keeps running behind the last two, so the next step picks the reader up where they left off); `actions` is what the step **does** to the running app as it opens (`click` or `type` by mark, `wait` for the gap a click opens). Every step stores its own `app` — there is no "same as before" value, and `newStep` copies the previous step's as a starting value. That is what makes dragging a step honest: nothing silently re-homes around it, and the control can always say truthfully what its step runs.
- **Runs are derived** (`appRuns`): consecutive steps holding the same `app`, which is what the rail bands. Never stored, so reordering can't put the grouping out of step with the steps. `bootsApp` is the step that loads the app — the first, or one whose app differs from the step before it — and only that step has a `start` (its hash route), because on the rest the app is already open and the reader may have moved around in it.
- **The ingest contract** (described in `src/walkthrough/types.ts`): an app has to hold up three rules — `data-walkthrough="<id>"` on anything a step points at or acts on (never CSS selectors, which rot), hash routes so a starting screen is an assignment rather than a load, and a build with `base: "./"`. `?wt=` is still sent, with no value: its presence is what tells an app it is in a walkthrough, so it can use fixtures rather than reaching for a backend. There are no seeds — an app opens in its default state for the screen it opens on. A `wt:signal` custom event covers what a click can't express ("the upload finished").
- **The driver** (`src/walkthrough/driver.ts`): the only way the player touches the demo, so how it reaches it stays swappable. `sameOriginDriver` reads the frame's document directly and needs nothing shipped inside the product; a cross-origin demo would need the same `Driver` interface implemented over postMessage against a small script in it. The frame's elements come from another realm, so recognise them by shape (`asElement`) — `instanceof Element` is always false across it. Pick mode is what lets the builder choose a mark by clicking the product.
- **Host integration** (`src/config.tsx`): the optional `CaseStudyProvider` supplies `assets` (`upload`/`list`/`libraryUrl`) and `useImageCaption`. Without `assets`, image fields are URL-only. `useImageCaption` is called as a hook, so it must be the same function on every render.
- **Project files** (`src/project.ts`): `migrate()` never throws. It fills defaults and stamps `schemaVersion` (`SCHEMA_VERSION`). Bump the version and add a migration step when the saved shape changes; additive optional fields need neither. Version 3 folded the privileged `target` and the named `targets` into one `stages` list; 4 removed the list entirely, giving every step its own `app`, `content` and `start`, and dropping seeds; 5 turned a case study's screens into steps that display them, which is what left one project type; 6 strips panel copy, the spotlight and the callouts from a step that displays a slide, since the slide covers both the panel and the stage. Old screens without a `theme` get one inferred at render time (`screenTheme`), not in migration. `withAssetBase` rewrites site-relative asset paths; it must cover every URL field on `Screen`/`ProjectPreview` and a step's image, embed and slide content, so update it when adding one. An ingested app's address is **not** rewritten: a step stores only the app's id, and where the pool is served from is the host's to say. `ProjectSummary`, one row of `index.json`, carries `count`, `preview` and `cover` — the first slide a project displays, or null for one that opens straight into an app. `kind` and `screens` went with the two project types.
- **Ingested apps** (`apps/<id>/`): the shared pool a walkthrough's steps run, served like `projects/` and copied into the build. Each folder is somebody's built output exactly as it came, plus an `app.json` naming it (`label`, `entry`, `width`, `minWidth`). It is a snapshot — ingesting copies the build in and never looks at the original again, so a demo can't break because the app it runs moved on. The pool sits at the root rather than inside a project because any walkthrough can run any app in it. `app/projects-plugin.ts` serves it and handles `/__apps/*` (ingest, rename, delete); the package never touches the filesystem, so `WalkthroughBuilder` takes `apps` plus the host's `onIngestApp`/`onPatchApp`/`onDeleteApp`.
- **ProjectBuilder** (`app/`, configured by the root `vite.config.ts` with `root: "app"`): hash routes `#/` (list), `#/<id>` (play), `#/<id>/edit`. Projects live in `projects/<id>/project.json` with images in `projects/<id>/images/`, and the folder is the single copy of a project that other sites load. `app/projects-plugin.ts` serves `projects/` from disk in dev, handles `/__projects/*` writes (create, save, publish, rename, duplicate, delete, upload), generates `projects/index.json` on request, and copies `projects/` into the build. A project with `draft: true` is left out of the build and its index; new projects and duplicates start as drafts, and save keeps the flag on disk, so only Publish on the list changes it. Editing is dev only (`canEdit = import.meta.env.DEV` in `app/store.ts`); the build is read-only. Image paths are stored as `/projects/<id>/images/<name>`. The build is deployed by Vercel (`vercel.json`) to `https://projects.tomcoggia.com`, with CORS open on `/projects/*`, and other apps (tomcoggia-com first) read it with `projectSource(base)` from `src/project.ts`, which makes image paths absolute. Projects are only authored here; consumers never store a copy. Which published projects a site shows is decided by that site, never by the project (`preview.show` is deprecated and ignored). Duplicate copies the images and rewrites those paths to the new id. Ids are slugs taken from the name when a project is created, and they never change.
- **Public API**: `src/index.ts` is the only entry point. Anything a host should use has to be exported there.

## Conventions

- **Controls come from `@tomcoggia/ui`** (`github:tomcog/component-library`), everywhere — the builders in `src/` and ProjectBuilder in `app/`. `Button` and `ButtonRound` for actions, `SegmentedControl`/`Segment` for a choice of which exactly one holds, `InputText`, `Tag`, `Card`. Don't hand-roll one of those; there is no longer a `primaryBtn`/`ghostBtn`/`iconBtn` to spread.
- It is a **peer dependency** of the package, not a bundled one: `src/` imports components from it, and the host imports the CSS (`@tomcoggia/ui/styles.css`, plus `@tomcoggia/ui/fonts.css` for DM Sans). A host that installs `@tomcog/case-study` has to install `@tomcoggia/ui` too, which is why the package never imports a stylesheet itself.
- What is still hand-styled in `src/` is **layout and the stage**: inline `style` objects, no CSS files or classNames apart from one scrollbar rule in `PhoneMockup`. Screens and the players stay that way on purpose — they render a reader's document, not an editor's chrome, so they take their look from the project data and the host page.
- Two groups stayed custom because the library has no component for them: the case-study **layout** and **theme** pickers, which are a ten-option and a four-option grid. `SegmentedControl` is a horizontal track and `RadioGroup` looks like radios; neither is a grid of ten.
- `app/app.css` is only the layout around the controls (list, tiles, messages), and names the font with the library's own chain (`var(--ui-font-family, var(--ui-font-primary), var(--ui-font-fallback))`) so the page and the components can't drift.
- Brand colors come from `src/theme.ts`. Rendering uses `RED`/`INK`, which are `var(--cs-accent, …)`/`var(--cs-ink, …)` so hosts can re-skin them. Values stored in project data (a screen's `accent`) must be real hex values (`DEFAULT_ACCENT`), never CSS variables.
- ESM with `moduleResolution: "Bundler"`: relative imports in `src/` use the `.js` extension (`./core.js`), even for `.tsx` sources.
- Files open with a short header comment (`// ─── Section ───`) describing their role. Match that style.
